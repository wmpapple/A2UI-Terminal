# S2.5 统一审阅流水线人工验收

> 状态：待用户人工验收  
> 实施基线：`main` / `93a8dcf` 之后的 S2.5 工作树  
> 数据库：SQLite schema v11  
> 阶段门禁：本文件验收通过前不得开始 S2.6

## 1. 验收目标

确认所有 AI 文件写入都先形成可持久恢复的 Review Request，由 Rust 重新校验后执行；用户可以逐块决定、处理并发冲突并撤销已应用修改。重点覆盖 AI 新建文本成果与已授权空白文件首次写入，确认接受前零写入、拒绝零副作用、重复应用幂等且绝不静默覆盖。

## 2. 准备

1. 使用虚构或脱敏资料建立测试工作区，不使用真实密钥、客户文档或个人资料。
2. 准备：
   - `notes.md`：至少两段非空、内容唯一的 Markdown；
   - `empty.md`：真正的零字节 UTF-8 文件；
   - 一个可使用的文本 Provider，或先用 Web Mock 验证界面闭环。
3. 记录应用 commit、Windows 版本、运行模式和诊断中的 schema 版本；预期 schema 为 `11`。
4. 记录“我的成果”目录开始时的文件数；不要把真实成果作为冲突试验对象。

## 3. 验收项目

### M01 — 迁移与旧数据保留

1. 从含现有工作区、会话、Result、Task 和版本记录的旧数据库启动本版本。
2. 打开原工作区、最近成果与历史版本。

预期：应用正常进入；schema 升至 v11；旧工作区、消息、成果、任务、版本和 Provider 非密钥配置仍在。迁移失败不得留下半张 `review_requests` 或 `review_blocks` 表。

### M02 — AI 新建成果接受前零写入

1. 新建对话，不选中任何现有文件作为修改目标。
2. 输入“生成一份杭州三日游文档”。
3. 完成发送清单确认，等待审阅中心出现。
4. 暂不点击接受，检查“我的成果”目录和成果列表。

预期：审阅显示建议文件名、应用管理目录、完整候选正文、理由和风险；此时没有空占位文件、Result 或 Revision，目录文件数不变。

### M03 — 拒绝创建零副作用

1. 在 M02 的审阅中点击“全部拒绝”。
2. 再次检查目录和成果列表。

预期：审阅关闭；没有创建文件、Result 或 Revision；重新启动应用也不会恢复已拒绝审阅。

### M04 — 调整名称、接受、幂等与撤销

1. 再次生成同类创建审阅。
2. 把建议名称改为一个安全的 `.md` 名称后接受。
3. 打开成果列表和历史，确认正文及初始版本。
4. 完全关闭并重新启动应用，从“我的成果”重新打开该成果，确认工具栏仍显示“撤销上次 AI 修改”。
5. 点击“撤销上次 AI 修改”。

预期：接受只产生一个真实文件、一个 Result 和一个初始 Revision；正文与审阅一致。重复应用由后端返回同一结果，不创建第二份（自动测试已直接覆盖重复 IPC）。重启后按钮由 SQLite 中的 Result→Review 关系恢复，不依赖前端临时状态。撤销成功后显示明确完成提示、自动回到“我的成果”，且该成果已经从列表消失；仅删除本次 AI 创建且尚未被后续修改的托管成果，再次撤销幂等。若接受后通过成果编辑器保存或从外部改过文件，撤销必须在当前成果页显示冲突原因并保留成果，不能静默无响应或删除用户新内容。

### M05 — 名称和路径安全

1. 按 M02 的方式生成一条新的创建型审阅：在右侧 AI 助手中新建对话，点击“上下文/修改发送清单”，取消当前文件、选区和其他现有文件目标，再输入“生成一份名称安全测试 Markdown 文档”。
2. AI 返回“完整候选内容已生成”后点击“前往审阅中心”；在创建块中找到有明确标签的“确认创建后的文件名”输入框。产品没有也不需要单独的“手工创建审阅”按钮，审阅是 AI 候选通过 Rust 校验后的结果。
3. 在该输入框中依次测试绝对路径（例如 `C:\temp\unsafe.md`）、`../unsafe.md`、子目录 `folder/unsafe.md`、Windows 保留名 `CON.md` 和非文本扩展名 `unsafe.exe`；每次点击“应用已选修改”，确认显示拒绝原因且没有创建成果，再改为下一个名称。
4. 最后把名称改成一个尚不存在的安全单层 `.md` 名称，确认可以继续接受；若只验证拒绝，可点击“全部拒绝”结束该审阅。
5. 同名冲突需使用另一条新的创建型审阅：先记下其建议文件名并暂不接受，进入“我的成果”使用用户主动新建入口创建同名 Markdown，再返回工作台恢复待审阅方案并点击接受。

预期：创建型审阅入口和文件名字段清晰可见；危险名称由 Rust 拒绝且 Review 保持可修正，磁盘零写入；同名文件进入冲突态，原成果正文保持不变，系统从不覆盖。前端提示不是唯一安全边界。

### M06 — 空白文件拒绝

1. 完全重启当前修复版本，另行创建并授权零字节 `empty.md`。
2. 打开该文件并等待超过 1 秒；从外部确认它没有因为编辑器初始化或自动保存变成一个换行。
3. 要求 AI“向这个空白 Markdown 写入首段内容”。
4. 在完整内容审阅中点击“全部拒绝”。

预期：出现 `replace_empty_file` 完整内容审阅，不再显示“AI 修改方案未通过安全校验”。接受前和拒绝后 `empty.md` 都保持零字节；系统没有伪造 Patch 锚点，也没有建立写入版本。由旧版本编辑器遗留的仅含空白/BOM 文件也可进入同一审阅，但拒绝和撤销会精确保留其原始字节；若要严格验证零字节门槛，请使用本步骤重新创建的文件。

### M07 — 空白文件接受与撤销

1. 重新生成 M06 的首次写入审阅并接受。
2. 检查文件内容和版本历史。
3. 点击“撤销上次 AI 修改”。

预期：仅发生一次写入；建立 Patch/Revision 审计；撤销后文件恢复为零字节，并新增可审计的撤销操作。

### M08 — 外部并发冲突三种选择

1. 让空白文件首次写入审阅停在待接受状态。
2. 在外部编辑器中写入并保存该文件，然后回到应用点击接受。
3. 分别用新的测试审阅验证：
   - “保留当前版本”；
   - “另存候选副本”；
   - “基于当前版本重新生成”。

预期：应用报告文件冲突，绝不覆盖外部正文。保留当前会关闭候选且不改原文件；另存副本把已审阅的完整候选保存到“我的成果”且不改原文件；重新生成关闭旧候选并提示基于最新文件重新发送。多文件冲突不会伪装成单一完整副本。

### M09 — 部分接受与恢复

1. 让 AI 对 `notes.md` 生成至少两个互不重叠的语义修改块。
2. 取消其中一个块，只接受另一个。
3. 检查磁盘后撤销。

预期：仅接受块生效，拒绝块不写入；撤销完整恢复应用前文件；审阅状态、Patch 操作和版本快照一致。

### M10 — 待审阅跨重启恢复

1. 生成创建型或修改型审阅，不做决定。
2. 正常关闭并重新启动应用，恢复同一工作区。

预期：最新待处理审阅自动回到审阅中心，完整块、文件名和风险不丢失；它来自 SQLite，而不是聊天 UI 临时状态。拒绝后再次重启不再恢复。

### M11 — 来源边界与后续阶段隔离

1. 验证聊天生成的文件修改进入统一审阅。
2. 触发当前 A2UI `request_patch` 中风险动作。
3. 检查选区助手是否出现新动作菜单。

预期：聊天写入使用统一 Review；A2UI 中风险动作仍只返回 `review_required`，不会直接写文件，真实 Action→Review 接线保留在 S3.3；S2.6 选区助手菜单尚未提前出现。用户主动手工编辑/主动新建仍走其既有安全保存或明确创建流程，不伪装成 AI Review。

### M12 — 工作区切换与自动保存隔离

1. 准备工作区 A、B，各放置一个相同相对路径（例如 `notes.md`）但正文显著不同的文件。
2. 在 A 中编辑 `notes.md`，立即通过最近工作区下拉切换到 B；等待至少 2 秒。
3. 在 B 中打开同名文件，确认正文后再快速往返切换 A、B 两次。
4. 分别用外部编辑器重新打开 A、B 的真实文件，并检查应用内版本历史。
5. 另用“添加文件”选择会建立不同独立文件工作区的文件，确认旧工作区 Tab、正文、选区和上下文不会带入。

预期：切换加载期间编辑器不可继续输入，旧自动保存计时器被取消；A 的草稿/保存只属于 A，B 始终保持自己的正文。旧编辑器回调、延迟保存响应、延迟打开文件响应和乱序完成的工作区请求都不能修改当前工作区；快速切换最终只显示最后一次选择。不同工作区即使有同名相对路径也不得串内容、串 Hash、串脏状态或触发错误自动保存。

### M13 — 成果位置、项目文件导航与阅读呈现

1. 新建对话，不选择可编辑目标，要求 AI“生成一份杭州三日游文档”。
2. 观察流式回复和完成回复，暂不接受审阅。
3. 接受 `create_file` 审阅，观察接受后的中心区域和成果标题区。
4. 点击“查看我的成果”，确认列表存在该成果；再打开它。
5. 点击左侧当前项目中的任意可读文件，再点击一次顶部“工作台”。
6. 在成果内切换“阅读 / 编辑”。

预期：聊天只显示“正在生成/已生成可审阅方案”和接受前零写入说明，不显示 `create_file`、`document_patch`、`replace_empty_file` JSON。接受后自动打开新成果；标题区明确显示“保存在‘我的成果’”，成果列表可重开。成果不应出现在左侧项目文件树，因为它不属于当前授权项目；底层绝对路径不暴露给前端。Markdown 默认按标题、列表和强调样式排版阅读，不显示 `#`、`**` 等源标记；切换到编辑后才显示源文。点击左侧项目文件必须立即回到工作区编辑器并打开所选文件；重新点击顶部“工作台”不得恢复一个过期的活动成果。

## 4. 已有自动证据

- Rust 端到端覆盖：创建接受前零写入、拒绝、应用、重复应用、名称冲突、危险路径、冲突副本、撤销；空文件拒绝、外部冲突、应用和撤销；待审阅数据库重开恢复；v11 迁移回滚。
- 共享 `contracts/v2/review.json` 同时由 Rust serde 与 TypeScript guard 校验。
- Web Mock E2E 覆盖“生成杭州三日游文档”完整内容审阅、拒绝、接受和撤销 UI 闭环。
- 命令注册测试校验 Review IPC 均在运行时、构建元数据和主窗口最小 Capability 中一致登记。
- 前端回归覆盖：编辑器跨工作区强制重建、旧回调拒绝、加载时取消自动保存、同名路径的延迟保存响应拒绝、不同文件工作区状态替换以及乱序恢复只接受最后选择。
- 成果/聊天回归覆盖：选择项目文件退出活动成果、新建 Review 接受后打开托管 Result、默认 Markdown 阅读视图与显式编辑切换、“我的成果”入口、AI 创建撤销，以及三种 Review JSON 均不作为聊天正文展示。
