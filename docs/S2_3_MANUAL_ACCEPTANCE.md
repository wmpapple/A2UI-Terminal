## 1. 本阶段交付结论

- 通用工作台在每个对话首次发送时主动展示两步清单：先“生成发送清单”，查看 Rust 实际复核结果，再“确认并发送”。同一对话后续请求仍由 Rust 逐次生成并消费新的 Manifest，但在已确认范围与 Provider 未变化、且没有新敏感风险时由前端后台完成，不再主动弹窗。
- 后续若发送范围、文件内容或 Provider 发生变化，系统只显示“发送范围有变化”并提示用户点击“修改发送清单”，不会抢占式打开弹窗；后台清单新发现敏感内容时同样等待用户主动点击并明确确认。
- 文件与表格通过已授权 `sourceId` 由 Rust 反查工作区归属并重新读取；前端不再把正文数组和 `sensitiveConfirmed` 直接塞进聊天请求。最终请求只携带一次性的 `contextManifestId`。
- 清单同时展示将发送来源、不会发送来源及原因、字符/Token 估算、本机/云端处理位置和敏感提示。未选择内容只形成无 Hash 的排除元数据，不读取进发送快照。
- 只有精确 `localhost`、`127.0.0.1`、`[::1]` 端点按本机处理；其他端点保守显示云端处理。切换 Provider 或修改其 Endpoint/Model/Temperature/Proxy 会使旧清单失效。
- 当前 Provider 合同是文本型 OpenAI-Compatible 请求，无法安全承载图片原始字节，因此图片在清单中明确显示“当前 Provider 合同不支持可信视觉输入；图片未发送”。表格由 Rust 按 S2.2 上限重新解析后作为结构化文本上下文发送。
- 待确认正文只在 Rust 内存保留最多 10 分钟；确认后只能消费一次。实际请求继续复用 SQLite `context_snapshots`，只保存清单元数据、Hash、排除原因和处理位置，不长期保存文件上下文正文。
- 本阶段没有实现 S2.4 的 Full/Retrieval/Hybrid、chunk、Embedding、索引、搜索或 Context Pack；成果专用 AI 区也没有绕过后续统一 Review 链路自动发送成果正文。

## 2. 验收准备

完全退出旧桌面开发实例，从仓库根目录启动：

```powershell
npm run tauri dev
```

准备不含真实隐私信息的测试资料：

1. `included.md`：写入一段可识别的普通文本。
2. `excluded.md`：写入另一段可识别文本，用于确认未勾选项不发送。
3. `table.csv`：小型基础表格。
4. `image.png`：小于 8 MB 的普通图片。
5. 可选敏感测试消息：只使用虚构值，例如 `API_KEY=fake-s2-3-test`，不要使用真实密钥。
6. 至少配置一个云端 Provider；可选配置一个明确 loopback 的自定义 Provider，例如 `http://localhost:11434/v1`。

## 3. 人工验收矩阵

### M01 — 每个对话首次请求主动展示 Rust 清单

1. 在通用工作台输入普通消息并点击“发送”。
2. 在弹窗中选择 `included.md`，取消选择 `excluded.md`。
3. 点击“生成发送清单”，不要立即发送。

预期：

- 弹窗不会关闭；主按钮变为“确认并发送”。
- 出现“Rust 可信发送清单”，`included.md` 位于“将发送”，`excluded.md` 位于“不会发送”且原因为“用户未选择”。
- 清单显示字符数、预计 Token 和当前处理位置。
- 关闭弹窗不会产生用户/助手消息，也不会调用 Provider。

结果：`待验收`

### M02 — 未选内容和图片不进入请求

1. 同时在候选中保留 `included.md`、未勾选 `excluded.md`，勾选 `image.png`。
2. 生成发送清单。

预期：

- `excluded.md` 只显示排除原因，不显示内容 Hash 或字符数。
- `image.png` 明确位于“不会发送”，原因为当前 Provider 合同不支持可信视觉输入；界面不声称 AI 已读取、OCR 或理解图片。
- `included.md` 是唯一文件正文来源；最近对话若未勾选，也明确列入排除项。

结果：`待验收`

### M03 — 表格由 Rust 复读并进入清单

1. 勾选 `table.csv` 并生成清单。

预期：

- 表格位于“将发送”，显示 Rust 计算的字符数与 Hash 元数据。
- S2.2 的行列、大小、公式不执行和公式注入限制仍生效；文件在授权后被替换、撤销或变为不合法时，生成清单失败而不是沿用前端旧内容。
- 不出现 Office/XLSX 无损结构或公式重新计算承诺。

结果：`待验收`

### M04 — Provider 切换立即更新位置并使旧清单失效

1. 使用云端 Provider 生成清单，确认顶部显示“云端处理”。
2. 不发送，进入“设置 → 专业模式 → 打开 Provider 高级设置”，切换到 loopback Provider；或修改当前 Provider 的 Endpoint/Model 并保存。
3. 返回工作台，不要主动打开清单。

预期：

- 输入区处理位置立即按新 Provider 更新；例如切到 `http://localhost:11434/v1` 后显示“本机处理”。
- 即使设置页导航使工作台组件卸载并重新挂载，页面仍显示“发送范围有变化”。升级前已有消息、尚无新版本审核基线的对话也必须显示该提示，不能错误显示“本会话已沿用”。点击“发送”只提示点击“修改发送清单”，不会主动弹窗或调用 Provider。
- 旧的 Rust 清单消失且不能继续使用；用户主动点击“修改发送清单”后必须按新 Provider 重新生成。
- 即使通过异常界面状态提交旧 `contextManifestId`，Rust 也返回“Provider 配置已变化/请重新确认”，不会调用 Provider。
- `https://localhost.evil.example` 等相似域名必须显示云端，不能被误判为本机。

结果：`待验收`

### M05 — 云端敏感内容可取消且必须单独确认

1. 选择云端 Provider，在消息中输入虚构测试值 `API_KEY=fake-s2-3-test`。
2. 生成清单。

预期：

- 出现敏感警告和额外确认复选框；未勾选时“确认并发送”不可用。
- 点击取消不会产生消息或网络请求。
- 勾选后才可发送；本地 loopback 仍显示敏感警告，但不把本地处理伪装成云端外发。
- 同一对话后续若后台 Manifest 新发现敏感内容，只出现点击“修改发送清单”的提示，不主动弹窗，也不自动代替用户勾选；用户主动打开后才可明确确认并发送。

结果：`待验收`

### M06 — 单对话一次主动弹窗、逐请求一次性消费与范围绑定

1. 正常确认并发送一条消息。
2. 尝试通过重试/开发工具重复提交同一清单，或在生成后修改 Prompt 再提交。

预期：

- 正常请求成功后，该 Manifest 已消费；重复使用被拒绝并要求重新确认。
- Prompt、工作区、会话或 Provider 任一变化都不能复用旧清单。
- 在发送范围和 Provider 未变化时输入第二条普通消息：界面不再打开确认弹窗，但 Rust 仍在后台生成、确认并消费一个绑定新 Prompt 的 Manifest；不能复用第一次的 Manifest ID。
- 切换当前文件、修改已选文件内容、增删来源或切换 Provider 后，状态变为“发送范围有变化”。此时点击“发送”只提示用户点击“修改发送清单”，不会主动打开弹窗，也不会调用 Provider。
- 用户主动点击“修改发送清单”后才能检查并保存新范围；如果输入框已有待发送 Prompt，范围变化时由该次主动点击进入可信清单确认流程。

结果：`待验收`

- 首次确认后入口显示“修改发送清单”和“本会话已沿用”；专业模式可显示 Provider 细节，但不能绕过逐请求的新 Manifest 与 Rust 绑定链路。

结果：`待验收`

### M08 — 审计与清理不保存文件上下文正文

预期：

- `context_snapshots.sources_json` 只包含 Manifest 元数据、Hash、排除原因和处理位置，不含文件正文、Prompt 正文、API Key、Endpoint 或绝对路径。
- 用户消息正文仍按既有会话策略本地保存；这与文件上下文快照不保存正文是两类数据。
- 待确认清单在应用退出、超时或“一键清除所有本地数据”后失效。
- 新命令只有 `allow-plan-context` 与 `allow-confirm-context-manifest` 最小权限；没有新增 Shell、任意文件、事件 emit、遥测或额外网络权限。

### M11 — 修改 Prompt 后旧清单立即失效

1. 在已有消息的会话中，通过云端 Provider 触发一份需要敏感确认的后台 Manifest，但不要打开或确认它。
2. 保持发送范围和 Provider 不变，修改输入框中的 Prompt。
3. 再次点击“发送”。

预期：

- 上一个 Prompt 生成的敏感清单立即失效，不能继续显示、确认或传给 `stream_chat`。
- 系统为新 Prompt 重新生成 Manifest；若新清单无需敏感确认，可以按后续消息规则在后台确认并发送。
- Rust 的 Prompt Hash 仍作为最终拒绝边界；前端不会依赖后端报错才发现清单过期。
- Manifest 规划期间输入框暂时不可编辑，避免用户以为规划中的请求已经被换成新文字。

结果：`待验收`
